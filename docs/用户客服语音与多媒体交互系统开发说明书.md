# 用户—客服语音与多媒体交互系统开发说明书

> 文档版本：V1.0  
> 编写日期：2026-08-31  
> 适用项目：AI Customer Service System  
> 目标读者：产品经理、前端工程师、后端工程师、测试工程师、运维工程师

## 1. 文档目的

本文说明如何在现有用户—客服文本会话系统中增量实现以下能力：

1. 用户和客服发送、接收、播放语音消息；
2. 将语音智能转写为文字，并把转写结果同步给会话双方；
3. 用户上传图片和常用文件，客服可预览或下载；
4. 在第二期支持用户与客服之间的实时语音通话；
5. 保证多租户隔离、消息幂等、断线恢复、文件安全和全链路可审计。

本文是代码实现说明，不代表上述功能已经完成。当前项目已具备 React 客户端、NestJS 后端、Prisma/MySQL、访客 JWT、会话 REST API、Socket.IO 事件和断线后 REST 对账；现阶段消息发送仍以文本为主。后续开发应复用已有会话权限、消息序号和实时事件机制，不另建一套相互独立的聊天系统。

## 2. 实施范围与优先级

### 2.1 第一期：异步多媒体消息闭环（必须）

- 语音录制、试听、取消和发送；
- 语音文件上传、播放、失败重试；
- 自动语音识别（ASR）和转写结果展示；
- 图片选择、压缩预览、上传和大图查看；
- 文件选择、上传进度、下载和失败重试；
- 文件格式、大小、数量校验和病毒扫描；
- Socket.IO 通知与断线后的 REST 对账；
- 用户端和客服工作台同时支持上述消息类型。

### 2.2 第二期：实时语音通话（建议）

- 呼叫、响铃、接听、拒绝、挂断；
- 麦克风开关、设备异常提示、网络质量提示；
- WebRTC 音频传输和 Socket.IO 信令；
- 可选录音、实时字幕、通话后转写；
- 通话记录、授权确认和审计。

### 2.3 暂不纳入首期

- 视频通话和屏幕共享；
- 多人会议；
- 大文件断点续传（超过 100 MB 时再引入分片上传）；
- 服务商绑定式 SDK。ASR、对象存储和病毒扫描均通过后端适配器接入。

## 4. 总体架构

### 4.1 多媒体消息链路

```text
用户/客服端
   │ 1. 请求上传凭证
   ▼
NestJS API ──鉴权/租户/类型/配额校验──► MySQL Attachment(pending)
   │ 2. 返回预签名上传地址
   ▼
对象存储（私有桶） ◄── 3. 浏览器直接上传文件
   │
   │ 4. 客户端通知上传完成
   ▼
NestJS API ──校验对象大小/摘要──► Attachment(scanning/ready)
   │                                  │
   │ 5. 创建 image/file/audio 消息   ├─ 图片缩略图任务
   ▼                                  ├─ 病毒扫描任务
MySQL Message                          └─ audio 触发 ASR 任务
   │
   └── Socket.IO: message.created / attachment.updated / transcription.updated
```

文件二进制不得经过 Socket.IO，也不建议经 NestJS 应用进程中转。生产环境采用“后端签发短时预签名地址、浏览器直传私有对象存储”的方式，减少应用服务器内存和带宽压力。

### 4.2 实时通话链路（第二期）

```text
用户端 ── Socket.IO 信令 ── NestJS ── Socket.IO 信令 ── 客服端
  │                                                       │
  └──────── WebRTC 音频：P2P 或经 SFU/TURN 中继 ──────────┘
```

Socket.IO 只传呼叫状态和 SDP/ICE 信令；实际音频由 WebRTC 传输。生产环境必须部署 TURN；若需要稳定录音、实时质检或大规模并发，应使用 SFU，而不是只依赖浏览器 P2P。

## 5. 数据模型设计

### 5.1 Message 扩展

现有 `Message` 已有 `messageType`、`metadata`、`fileId`、`fileName` 和 `fileSize`。建议数据库迁移时把 `fileId` 明确升级为 `attachmentId`（迁移旧数据后再删除旧列）；若首期必须兼容旧接口，也可暂时让 DTO 同时接受两者，但服务层应立即归一化为 `attachmentId`，不能长期维护两个真实来源。`MessageType` 增加 `audio`：

```prisma
enum MessageType {
  text
  richtext
  image
  file
  audio
  system
}
```

`Message` 与附件建立可空的一对一引用：

```prisma
model Message {
  // 保留现有字段
  attachmentId String?      @unique @db.VarChar(64)
  attachment   Attachment? @relation(fields: [attachmentId], references: [id])
  transcription Transcription?
}
```

消息内容约定：

- `text`：`content` 必填；
- `image/file/audio`：`attachmentId` 必填，`content` 可作为用户说明；
- 音频转写不覆盖用户原消息，写入 `Transcription`，便于保留原始证据和重新转写。

### 5.2 Attachment 表

```prisma
enum AttachmentKind {
  image
  file
  audio
}

enum AttachmentStatus {
  pending
  uploaded
  scanning
  ready
  rejected
  deleted
}

model Attachment {
  id             String           @id @db.VarChar(64)
  tenantId       String           @db.VarChar(64)
  uploaderId     String           @db.VarChar(64)
  conversationId String           @db.VarChar(64)
  kind           AttachmentKind
  status         AttachmentStatus @default(pending)
  objectKey      String           @unique @db.VarChar(512)
  originalName   String           @db.VarChar(255)
  mimeType       String           @db.VarChar(128)
  sizeBytes      BigInt
  sha256         String?          @db.Char(64)
  width          Int?
  height         Int?
  durationMs     Int?
  thumbnailKey   String?          @db.VarChar(512)
  rejectReason   String?          @db.VarChar(255)
  message        Message?
  createdAt      DateTime         @default(now())
  updatedAt      DateTime         @updatedAt

  @@index([tenantId, conversationId, createdAt])
  @@index([tenantId, status, createdAt])
}
```

`objectKey` 推荐格式：`tenant/{tenantId}/conversation/{conversationId}/{attachmentId}/{safeFileName}`。不要把租户上传的原始文件名直接作为完整对象键，也不要把对象存储的永久公开 URL 写入数据库。

### 5.3 Transcription 表

```prisma
enum TranscriptionStatus {
  pending
  processing
  succeeded
  failed
}

model Transcription {
  id             String              @id @db.VarChar(64)
  tenantId       String              @db.VarChar(64)
  messageId      String              @unique @db.VarChar(64)
  attachmentId   String              @db.VarChar(64)
  status         TranscriptionStatus @default(pending)
  language       String?             @db.VarChar(20)
  text           String?             @db.Text
  confidence     Float?
  provider       String?             @db.VarChar(40)
  providerTaskId String?             @db.VarChar(128)
  errorCode      String?             @db.VarChar(40)
  attemptCount   Int                 @default(0)
  message        Message             @relation(fields: [messageId], references: [id], onDelete: Cascade)
  createdAt      DateTime            @default(now())
  updatedAt      DateTime            @updatedAt

  @@index([tenantId, status, createdAt])
}
```

### 5.4 VoiceCall 表（第二期）

至少记录 `id`、`tenantId`、`conversationId`、`callerId`、`calleeId`、`status`、`startedAt`、`answeredAt`、`endedAt`、`endedReason`、`recordingConsentAt`、`recordingAttachmentId` 和 `transcriptionId`。通话状态只允许：

```text
initiated → ringing → connected → ended
                    ↘ rejected
                    ↘ missed
```

所有状态迁移在服务端校验，客户端不能直接把任意状态写进数据库。

## 6. REST API 设计

所有接口沿用 `/api/v1`、Bearer JWT、统一响应包裹和现有租户权限规则。客户只能操作自己的会话；客服只能操作自己可查看或已接管的会话；平台管理员访问租户数据时继续显式指定目标租户。

### 6.1 初始化上传

`POST /api/v1/conversations/:conversationId/attachments/init`

请求：

```json
{
  "clientUploadId": "UUID",
  "kind": "audio",
  "fileName": "voice.webm",
  "mimeType": "audio/webm",
  "sizeBytes": 183421,
  "sha256": "可选的64位十六进制摘要",
  "durationMs": 12600
}
```

响应：

```json
{
  "attachmentId": "att_xxx",
  "uploadUrl": "短时有效的预签名URL",
  "method": "PUT",
  "headers": { "Content-Type": "audio/webm" },
  "expiresAt": "2026-08-31T10:05:00.000Z"
}
```

后端关键步骤：

1. 校验用户是否能查看该会话；
2. 校验 `kind`、MIME、扩展名、声明大小、租户配额；
3. `clientUploadId + conversationId` 做唯一约束，防止重复初始化；
4. 生成不可预测的 `attachmentId` 和私有 `objectKey`；
5. 写入 `Attachment(pending)`；
6. 返回 5 分钟左右有效的预签名上传地址。

### 6.2 确认上传完成

`POST /api/v1/attachments/:attachmentId/complete`

后端不能只相信客户端的“完成”通知，必须向对象存储执行 HEAD，核对对象是否存在、实际大小、Content-Type 和可选摘要。核对成功后将状态改为 `uploaded/scanning`，触发病毒扫描和媒体元数据提取。

### 6.3 创建多媒体消息

沿用现有端点：`POST /api/v1/conversations/:id/messages`

扩展后的 DTO：

```ts
export class SendMessageDto {
  @IsUUID()
  clientMessageId!: string;

  @IsEnum(MessageType)
  messageType: MessageType = MessageType.text;

  @ValidateIf((value) => value.messageType === MessageType.text)
  @IsString()
  @Length(1, 5000)
  content?: string;

  @ValidateIf((value) => value.messageType !== MessageType.text)
  @IsString()
  attachmentId?: string;
}
```

服务层创建消息前必须验证：

- 附件属于当前租户、当前会话和当前上传人；
- 附件状态为 `ready`，被拒绝或尚在扫描的附件不可发消息；
- `messageType` 与附件 `kind` 一致；
- 同一个附件最多绑定一条正常消息；
- 继续使用现有 `clientMessageId` 幂等、`reserveSequence()` 消息序号和事务锁；
- 创建成功后继续广播 `message.created`，不传二进制。

音频消息创建完成后，在事务提交成功后投递 ASR 任务。不要在数据库事务内同步等待第三方识别接口。

### 6.4 获取和下载附件

- `GET /api/v1/attachments/:id`：返回元数据及短时预览/下载 URL；
- `POST /api/v1/attachments/:id/download-url`：按权限签发短时下载 URL；
- `GET /api/v1/messages/:messageId/transcription`：查询转写状态；
- `POST /api/v1/messages/:messageId/transcription/retry`：仅失败任务可重试，并限制次数和频率。

图片预览 URL 建议有效期 5～15 分钟；下载 URL 建议使用 `Content-Disposition: attachment`。客户端不能缓存永久 URL，过期后重新请求。

### 6.5 建议限制

| 类型 | 首期限制 | 建议格式 |
| --- | ---: | --- |
| 图片 | 单张 10 MB，每次最多 9 张 | JPEG、PNG、WebP、GIF（可选） |
| 普通文件 | 单个 50 MB，每次最多 5 个 | PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、TXT、CSV、ZIP（按业务决定） |
| 语音 | 单条 5 分钟、20 MB | WebM/Opus、Ogg/Opus、M4A/AAC |

前端校验用于及时提示，后端必须再次校验。MIME、扩展名和文件魔数三者冲突时拒绝文件。

## 7. 前端实现步骤

### 7.1 统一消息模型

扩展 `normalizeMessage`，让客户 Widget 和客服工作台共享同一结构：

```js
export function normalizeMessage(message) {
  return {
    id: message.id,
    sequence: message.sequence,
    clientMessageId: message.clientMessageId,
    senderType: message.senderType,
    messageType: message.messageType || 'text',
    content: message.content || '',
    attachment: message.attachment || null,
    transcription: message.transcription || null,
    deliveryStatus: message.deliveryStatus || 'accepted',
    createdAt: message.createdAt,
  }
}
```

`MessageContent` 只负责按类型渲染，消息气泡的发送方、时间、已读状态仍由外层统一处理：

```jsx
function MessageContent({ message }) {
  switch (message.messageType) {
    case 'image': return <ImageMessage message={message} />
    case 'file': return <FileMessage message={message} />
    case 'audio': return <VoiceMessage message={message} />
    default: return <span>{message.content}</span>
  }
}
```

### 7.2 上传状态机

每个待上传项目维护以下状态：

```text
selected → initializing → uploading → confirming → sending → sent
                      ↘ failed（允许从失败步骤重试）
                      ↘ cancelled
```

上传队列中保存 `localId`、`File/Blob`、文件名、类型、大小、预览 URL、进度、错误信息和服务端 `attachmentId`。组件卸载或项目删除时调用 `URL.revokeObjectURL()`，避免本地预览内存泄漏。

建议流程：

```js
async function uploadAndSend({ conversationId, file, kind, client }) {
  const clientUploadId = crypto.randomUUID()
  const init = await client.rest.initAttachment(conversationId, {
    clientUploadId,
    kind,
    fileName: file.name,
    mimeType: file.type,
    sizeBytes: file.size,
  })

  await putWithProgress(init.uploadUrl, file, init.headers)
  await client.rest.completeAttachment(init.attachmentId)
  return client.rest.sendConversationMessage(conversationId, {
    clientMessageId: crypto.randomUUID(),
    messageType: kind,
    attachmentId: init.attachmentId,
  })
}
```

需要展示真实上传进度时可使用 `XMLHttpRequest.upload.onprogress`；若只使用 `fetch`，多数浏览器环境无法直接获得请求体上传进度。

### 7.3 图片交互

1. 使用 `<input type="file" accept="image/jpeg,image/png,image/webp">`；
2. 选中后立即在前端校验数量、大小和类型；
3. 使用对象 URL 显示本地缩略图并允许删除；
4. 可选地在浏览器端压缩超大照片，但不能以压缩替代后端限制；
5. 逐个或限并发 2～3 个上传，避免弱网同时占满带宽；
6. 消息中展示缩略图，点击后打开带键盘关闭、焦点管理和下载按钮的大图查看器；
7. 图片加载失败时显示文件名和“重新获取预览地址”。

不要把图片转换成 Base64 放进消息 JSON 或 localStorage；这会显著放大体积并阻塞渲染。

### 7.4 文件交互

文件卡片至少显示：文件类型图标、原始文件名、大小、上传/扫描状态、下载按钮。文件名使用文本节点渲染，禁止用 `dangerouslySetInnerHTML`。用户取消上传时中断 XHR，并调用后端取消/清理接口；后端定时清理长期处于 `pending` 且没有消息引用的对象。

### 7.5 语音录制

录音组件状态机：

```text
idle → requesting_permission → recording → preview → uploading → sent
                       ↘ denied/error      ↘ cancelled
```

关键实现：

```js
async function startRecording() {
  const stream = await navigator.mediaDevices.getUserMedia({
    audio: {
      echoCancellation: true,
      noiseSuppression: true,
      autoGainControl: true,
    },
  })
  const mimeType = pickSupportedAudioMimeType()
  const recorder = new MediaRecorder(stream, mimeType ? { mimeType } : undefined)
  const chunks = []
  recorder.ondataavailable = (event) => {
    if (event.data.size > 0) chunks.push(event.data)
  }
  recorder.onstop = () => {
    const blob = new Blob(chunks, { type: recorder.mimeType })
    stream.getTracks().forEach((track) => track.stop())
    createPreview(blob)
  }
  recorder.start(1000)
}
```

实现时还必须处理：

- 页面必须处于 HTTPS 或 localhost；
- 用户拒绝麦克风权限时给出浏览器设置指引；
- 开始录音前检查 `MediaRecorder`，不支持时隐藏按钮或提示改用文件上传；
- 用 `MediaRecorder.isTypeSupported()` 按 `audio/webm;codecs=opus`、`audio/ogg;codecs=opus`、浏览器默认格式依次选择；
- 限制最短 1 秒、最长 5 分钟，达到上限自动停止；
- 显示时长和简单音量反馈；切后台、设备断开、权限撤销时安全停止；
- 停止或取消后关闭全部 `MediaStreamTrack`；
- 发送前允许试听和删除，不要停止录音后立即不可撤销地发送。

### 7.6 语音播放

`VoiceMessage` 展示播放/暂停、时长、进度、倍速和转写文本。列表中只允许一个音频同时播放，可由父级保存 `playingMessageId`。切换会话或组件卸载时暂停音频并释放引用。

建议 UI 状态：

- `pending/processing`：显示“正在转写…”；
- `succeeded`：默认折叠，点击“查看文字”展开；
- `failed`：显示“转写失败”，具备权限的用户可重试；
- 置信度低时标记“识别结果可能不准确”，不要把识别文本伪装成用户亲自输入的文本。

### 7.7 断线和重试

现有系统的原则保持不变：REST 是权威数据，Socket.IO 只负责实时提示。

1. `message.created` 到达后按 `message.id/clientMessageId` 去重；
2. 增加 `attachment.updated` 和 `transcription.updated` 订阅，只更新对应消息；
3. Socket 重连后调用 `GET /conversations/:id` 重拉完整会话；
4. 上传过程中断网时项目保留在本地队列，恢复后由用户点击重试；
5. 消息创建超时但结果未知时，必须用相同 `clientMessageId` 重试；
6. 页面刷新后的恢复只保存必要元数据。浏览器 `File/Blob` 默认不可从 localStorage 恢复，若确需恢复应使用 IndexedDB。

## 8. 智能语音转文字（ASR）实现

### 8.1 任务流程

```text
audio 消息创建
  → 新建 Transcription(pending)
  → 投递队列任务
  → Worker 下载私有音频
  → 必要时转码/切片
  → 调用 ASR Provider
  → 保存文本、语言、置信度
  → 发布 transcription.updated
  → 失败按策略重试或进入失败终态
```

生产环境建议用 Redis/BullMQ、RabbitMQ 或现有消息队列执行异步任务。单机开发可先用数据库任务表 + 定时扫描，但控制器请求中不能同步等待长音频识别。

### 8.2 Provider 抽象

```ts
export interface SpeechToTextProvider {
  transcribe(input: {
    audioStream: NodeJS.ReadableStream;
    mimeType: string;
    languageHint?: string;
    requestId: string;
  }): Promise<{
    text: string;
    language?: string;
    confidence?: number;
    segments?: Array<{ startMs: number; endMs: number; text: string }>;
    providerTaskId?: string;
  }>;
}
```

业务服务只依赖接口，不直接依赖具体云厂商。Provider 负责鉴权、请求格式、超时和供应商错误映射；API Key 必须在服务端通过密钥管理或环境变量读取，绝不能返回浏览器。

### 8.3 转码和语言策略

- 保留用户原始音频作为证据文件；
- 若 ASR 不支持浏览器原格式，由 Worker 用 FFmpeg 转成单声道、16 kHz PCM/WAV；
- 优先自动识别语言，可结合租户默认语言作为提示；
- 中英文混说场景必须纳入测试；
- 超长音频按静音点切片，片段带时间戳，最终按顺序合并；
- 识别文本仅做空白和标点规范化，不擅自改写用户原意；
- 若要做摘要、意图识别或情绪分析，应建立独立派生任务，不能覆盖 ASR 原文。

### 8.4 重试与幂等

- `messageId` 对 `Transcription` 唯一，重复消费同一任务不会重复建记录；
- 网络超时、限流、供应商 5xx 可指数退避重试，例如 10 秒、30 秒、2 分钟；
- 格式不支持、文件损坏、时长超限属于永久失败，不自动重试；
- 默认最多自动重试 3 次；
- Provider 回调需校验签名，按 `providerTaskId` 幂等更新；
- 每次状态改变均写操作日志，但日志中不记录音频正文、签名 URL 或密钥。

### 8.5 可选文字转语音（TTS）

如果“语音交互”还要求系统把 AI/客服文字读给用户，可增加：

`POST /api/v1/messages/:messageId/speech`

后端检查该消息对当前用户可见后，将文字投递 TTS 任务，生成一个只读音频附件，并通过 `speech.generated` 通知客户端。相同 `messageId + voice + speed` 应使用缓存，避免重复计费。首期也可以只使用浏览器 `speechSynthesis` 做无持久化辅助朗读，但各浏览器音色不一致，且不适合作为正式客服录音。

## 9. 实时语音通话实现（第二期）

### 9.1 发起与信令事件

建议先通过 REST 创建通话记录：

`POST /api/v1/conversations/:id/voice-calls`

然后通过已有 Socket.IO 身份认证通道传递：

| 事件 | 方向 | 说明 |
| --- | --- | --- |
| `voice.call.invited` | 服务端 → 被叫方 | 新呼叫、来电信息和超时点 |
| `voice.call.accept` | 被叫方 → 服务端 | 接听 |
| `voice.call.reject` | 被叫方 → 服务端 | 拒绝 |
| `voice.call.offer` | 点对点经服务端转发 | SDP offer |
| `voice.call.answer` | 点对点经服务端转发 | SDP answer |
| `voice.call.ice-candidate` | 点对点经服务端转发 | ICE candidate |
| `voice.call.end` | 任一方 → 服务端 | 挂断 |
| `voice.call.updated` | 服务端 → 双方 | 权威通话状态 |

每个信令载荷必须包含 `callId`，服务端根据通话参与者鉴权，禁止客户端自行指定任意目标用户。SDP 和 ICE 不落业务日志正文，只记录事件类型和 requestId。

### 9.2 浏览器端 WebRTC 关键步骤

1. 用户点击发起/接听后再申请麦克风权限；
2. 创建 `RTCPeerConnection({ iceServers })`；
3. 将麦克风轨道 `addTrack()` 到连接；
4. 发起方创建 offer，被叫方设置远端描述并创建 answer；
5. 双方交换 ICE candidate；
6. `ontrack` 收到远端音频并绑定 `<audio autoPlay>`；
7. 监听 `connectionState`，失败时提示重连或回退为语音消息；
8. 挂断时关闭 `RTCPeerConnection`、停止所有轨道，并幂等通知服务端；
9. 服务端设置振铃超时，例如 30 秒，超时状态改为 `missed`。

### 9.3 TURN/SFU 与录音

- 开发环境可先测试 P2P + STUN；生产环境必须配置带短期凭证的 TURN；
- 需要服务端录音、实时字幕、质检或多人扩展时采用 SFU；
- 录音前必须向双方明确提示并取得授权，记录授权时间；
- 录音文件仍进入 Attachment 安全链路，再异步转写；
- 未取得授权时不得偷偷录制，也不得仅依赖前端开关作为合规依据。

## 10. 后端模块职责与关键代码步骤

### 10.1 AttachmentsModule

- `AttachmentsController`：初始化、确认、获取下载地址、取消；
- `AttachmentsService`：会话权限、配额、状态机和数据库事务；
- `ObjectStoragePort`：`createUploadUrl/headObject/createDownloadUrl/deleteObject`；
- `MediaInspector`：文件魔数、图片尺寸、音频时长；
- `MalwareScanner`：扫描并把状态改为 `ready/rejected`；
- `OrphanCleanupJob`：删除超时未完成且无消息引用的附件。

### 10.2 ConversationsService 改造

对现有 `sendMessage()` 做最小扩展：

1. 保留 `findConversation`、`assertCanView`、`canReplyToConversation`；
2. 文本消息沿用当前校验；
3. 多媒体消息额外查询并锁定附件；
4. 在同一事务内复用 `reserveSequence()`、创建 `Message`、更新会话最后消息时间和写 `ConversationEvent`；
5. 事务提交后广播 `message.created`；
6. 若为音频，提交 ASR 任务；
7. 若任务提交失败，消息仍保留，转写状态置为失败或由补偿任务恢复，不能回滚用户已发送的音频。

### 10.3 Realtime 扩展

在现有事件白名单中增加：

```js
'attachment.updated'
'transcription.updated'
'voice.call.invited'
'voice.call.updated'
'speech.generated'
```

事件建议统一包含：

```json
{
  "eventId": "UUID",
  "eventType": "transcription.updated",
  "tenantId": "tenant_xxx",
  "conversationId": "conv_xxx",
  "occurredAt": "2026-08-31T10:00:00.000Z",
  "data": { "messageId": "msg_xxx", "status": "succeeded" }
}
```

事件中只带状态和资源 ID；正文可在权限校验后的 REST 详情中取得。这样可减少敏感数据在广播层扩散。

## 11. 安全、隐私与合规

1. 对象存储桶保持私有，禁止匿名读和永久公开 URL；
2. 上传和下载均先校验 JWT、租户、会话归属和角色权限；
3. 文件名清理路径字符，服务端对象键不使用用户原始路径；
4. 使用白名单格式、大小上限、魔数识别、病毒扫描和压缩包策略；
5. HTML/SVG 等可执行内容默认禁止在线预览，统一下载；
6. 图片服务设置正确 `Content-Type`、`Content-Disposition` 和安全响应头；
7. 语音和转写属于敏感会话内容，遵循与聊天记录相同或更严格的保留、导出和删除策略；
8. 第三方 ASR 若会把数据传出部署区域，须在租户配置和隐私政策中明确说明；
9. 日志中只记录 ID、耗时、状态、大小和错误码，不记录访问签名、原始语音、完整转写或 API Key；
10. 对上传初始化、下载签名、ASR 重试和通话邀请实施用户级与租户级限流；
11. 删除消息时按产品规则决定软删除还是撤回，但附件只有在确认无引用且超过保留期后才能物理删除；
12. 所有管理操作写入现有审计日志，包含操作者、租户、目标、requestId 和前后状态。

## 12. 异常处理与用户提示

| 场景 | 系统处理 | 用户提示 |
| --- | --- | --- |
| 麦克风权限被拒绝 | 不创建录音任务 | “无法使用麦克风，请在浏览器设置中允许后重试” |
| 浏览器不支持录音 | 隐藏/禁用录音入口 | “当前浏览器不支持录音，可上传音频文件” |
| 文件过大/格式不允许 | 前后端均拒绝 | 明确显示限制，不只显示“上传失败” |
| 上传中断 | 保留队列项，可重试 | “网络中断，点击重试” |
| 扫描不通过 | 附件 `rejected`，不可建消息 | “文件未通过安全检查” |
| 消息请求超时 | 相同幂等 ID 重试并对账 | “正在确认发送结果” |
| ASR 暂时失败 | 自动退避重试 | “转写暂不可用，语音仍可播放” |
| ASR 永久失败 | 保留音频，允许人工重试 | “未能识别此段语音” |
| 通话网络失败 | 结束通话并释放资源 | “通话连接失败，可改发语音消息” |
| 签名 URL 过期 | 重新获取 URL | 对用户无感刷新，失败后再提示 |

错误响应沿用系统统一格式，并为新增场景分配稳定业务码，例如附件不存在、格式不支持、扫描未完成、附件越权、ASR 任务不可重试、通话状态冲突等。

## 13. 测试方案

### 13.1 前端单元测试

- MIME/扩展名/大小/时长校验；
- 录音状态机的开始、停止、取消、权限拒绝和超时；
- 上传状态机及从失败步骤重试；
- `normalizeMessage` 对 text/image/file/audio 的兼容；
- `MessageContent` 正确选择组件；
- Socket 重复事件不会重复插入消息；
- 转写状态更新只影响目标消息；
- 切换播放时自动暂停上一条音频。

在 Node 测试中 mock `MediaRecorder`、`mediaDevices.getUserMedia`、XHR 和对象 URL。

### 13.2 后端单元测试

- 不同角色和租户的附件访问策略；
- 附件状态机不允许非法跳转；
- 多媒体消息与附件类型一致性；
- 重复 `clientUploadId/clientMessageId` 幂等；
- ASR Provider 错误分类和重试策略；
- 回调签名、回调幂等和最大重试次数；
- 通话状态机和参与者鉴权。

### 13.3 E2E 测试

至少覆盖：

1. 访客获取 JWT，创建会话；
2. 初始化图片上传、模拟对象存储完成、扫描通过、发送图片消息；
3. 客服通过 Socket 收到消息，再通过 REST 获取一致详情；
4. 上传音频、发送音频消息、Worker 完成转写，双方收到转写更新；
5. 上传失败后使用相同上传 ID 重试，不重复创建附件；
6. 其他租户不能获取预览/下载 URL；
7. 被拒绝附件不能创建消息；
8. Socket 断开期间产生消息，重连后 REST 对账完整；
9. 通话邀请、接听、挂断和超时的状态迁移（第二期）。

### 13.4 浏览器和弱网测试

至少验证桌面 Chrome/Edge、Safari 和移动端主流 WebView。重点测试：权限首次询问、永久拒绝、切后台、锁屏、耳机插拔、2G/3G 弱网、上传中断、Socket 重连、URL 过期和多个附件并发。

## 14. 监控指标

- 上传初始化成功率、上传确认成功率和 P95 耗时；
- 各 MIME/大小区间失败分布；
- 病毒扫描队列长度、耗时和拒绝数量；
- ASR 成功率、P50/P95 时延、重试率、分钟数和供应商错误码；
- 多媒体消息发送成功率和幂等命中次数；
- 孤儿附件数量与清理量；
- 实时通话呼叫成功率、接通率、平均接通时间、异常断线率；
- TURN 中继比例、丢包、抖动和 RTT（第二期）。

告警建议：ASR 连续 5 分钟成功率低于阈值、扫描队列堆积、对象存储错误率异常、孤儿附件快速增长、TURN 不可用或通话异常断线率升高。

## 15. 推荐开发顺序与验收标准

### 阶段 A：数据和上传基础

1. Prisma 增加 `Attachment`、`Transcription` 和 `audio` 类型；
2. 实现对象存储适配器、初始化/确认/下载接口；
3. 实现文件安全校验和清理任务；
4. 用接口测试验证租户隔离、幂等和状态机。

验收：授权用户可上传并获取短时下载地址；跨租户访问被拒绝；不合规文件不能进入 `ready`。

### 阶段 B：图片和文件消息

1. 扩展消息 DTO、服务和归一化模型；
2. 开发上传队列、图片消息、文件消息组件；
3. 客户 Widget 与客服工作台接入统一组件；
4. 增加 Socket 通知和 REST 对账测试。

验收：双方可以稳定发送、预览/下载图片与文件；刷新、重连和重复请求不会丢失或重复消息。

### 阶段 C：语音消息和 ASR

1. 开发 `VoiceRecorder` 和 `VoiceMessage`；
2. 实现音频元数据校验与上传；
3. 实现 ASR Provider、异步任务、重试和状态通知；
4. 完成中英文、弱网、权限拒绝和格式兼容测试。

验收：用户能录制、试听、取消和发送；语音可播放；转写异步出现；转写失败不影响原语音；双方刷新后结果一致。

### 阶段 D：实时语音通话

1. 建立 VoiceCall 状态机和鉴权信令；
2. 完成 WebRTC P2P 原型和 TURN；
3. 增加设备、网络、挂断和超时处理；
4. 按需求接入 SFU、录音和实时字幕。

验收：授权会话双方可呼叫、接听、拒绝和挂断；越权用户不能加入；弱网失败能正确清理并回退到语音消息。

## 16. 完成定义（Definition of Done）

功能只有在同时满足以下条件时才算完成：

- 客户端和客服端均可使用，不是单端演示；
- 数据库迁移可重复部署，Swagger 展示新增接口；
- REST、Socket 和数据库三者最终一致；
- 租户隔离、角色权限、文件安全、限流和审计已验证；
- 所有新增状态均有加载、成功、失败、重试和只读展示；
- 单元测试、E2E 测试、前端构建和后端构建通过；
- 监控指标可观测，第三方服务失败时语音原件和聊天主链路仍可用；
- 运维文档明确对象存储、ASR、队列、FFmpeg、TURN/SFU 的环境配置及密钥来源；
- 隐私政策、录音授权和数据保留规则经业务负责人确认。

---

本方案的核心原则是：多媒体内容通过私有对象存储承载，消息记录只保存受控引用；ASR 和媒体处理异步执行；Socket.IO 负责通知，REST 负责权威对账；实时通话使用 WebRTC，继续复用现有 JWT、租户权限、会话归属和审计体系。
