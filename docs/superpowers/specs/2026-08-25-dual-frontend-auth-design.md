# 双前端入口与四角色认证原型设计

## 1. 目标

将现有“四种身份集中在同一登录注册页面”的认证原型，重构为两个独立访问入口：

- 客服与用户系统：面向客服人员和普通用户。
- 平台与租户管理系统：面向超级管理员和租户管理员。

两个入口共用现有 React 工程、后端认证接口、数据库和会话模型，但在页面、角色选项、路由守卫和登录后首页上保持清晰边界。

第一阶段要求普通用户必须注册并登录后才能发起咨询，不提供匿名访客聊天。

## 2. 范围

### 2.1 本期包含

- 重新设计两套独立的登录、注册和找回密码界面。
- 将四种注册身份拆分到两个入口，每个入口只显示两种身份。
- 根据登录角色跳转到不同的业务页面。
- 未登录访问受保护页面时，返回所属系统的登录页。
- 普通用户登录后进入受保护的客户聊天页面。
- 继续使用现有后端注册、登录接口和数据库角色字段。
- 保留现有平台后台、租户后台、客服工作台和客户聊天界面。

### 2.2 本期不包含

- 匿名访客咨询。
- 第三方单点登录、短信登录和社交账号登录。
- 两个独立构建产物或两个独立前端仓库。
- 对现有后端角色模型进行大规模重构。
- 客户聊天功能的二期精细化能力。

## 3. 技术方案

采用“单一 React 应用、两个路由命名空间”的结构。该方案能形成两个独立浏览器入口，同时复用现有组件和接口，避免维护两份重复前端工程。

### 3.1 客服与用户系统

| 页面 | 路由 | 可选身份 |
| --- | --- | --- |
| 登录 | `/service/login` | 客服、用户 |
| 注册 | `/service/register` | 客服、用户 |
| 找回密码 | `/service/forgot-password` | 客服、用户 |
| 客服首页 | `/workbench` | 客服 |
| 用户咨询页 | `/customer/chat` | 用户 |

### 3.2 平台与租户管理系统

| 页面 | 路由 | 可选身份 |
| --- | --- | --- |
| 登录 | `/admin/login` | 超级管理员、租户管理员 |
| 注册 | `/admin/register` | 超级管理员、租户管理员 |
| 找回密码 | `/admin/forgot-password` | 超级管理员、租户管理员 |
| 平台首页 | `/platform/overview` | 超级管理员 |
| 租户首页 | `/organization/overview` | 租户管理员 |

### 3.3 兼容路由

- `/login` 重定向到 `/service/login`。
- `/register` 重定向到 `/service/register`。
- `/forgot-password` 重定向到 `/service/forgot-password`。
- `/chat` 重定向到受保护的 `/customer/chat`。

兼容路由仅用于旧链接过渡，不再展示四身份混合页面。

## 4. 身份与跳转规则

登录页面不允许用户自行提升权限。最终角色以服务端登录响应为准。

| 角色字段 | 所属入口 | 登录后首页 |
| --- | --- | --- |
| `platform_admin` | 平台与租户管理系统 | `/platform/overview` |
| `tenant_admin` | 平台与租户管理系统 | `/organization/overview` |
| `agent` | 客服与用户系统 | `/workbench` |
| `customer` | 客服与用户系统 | `/customer/chat` |

若账号角色与当前登录入口不匹配，页面不创建前端会话，并提示用户前往正确的系统入口。

## 5. 注册流程

### 5.1 客服注册

- 字段：姓名、邮箱、密码、确认密码、所属机构。
- 接口：沿用客服注册接口。
- 注册成功后返回 `/service/login`。

### 5.2 用户注册

- 字段：姓名、邮箱、手机号（可选）、来源、所属机构。
- 用户必须具备可登录凭据；若当前客户注册接口未接收密码，需要在实施阶段补齐密码字段和认证账号关联。
- 注册成功后返回 `/service/login`。

### 5.3 超级管理员注册

- 字段：姓名、邮箱、密码、确认密码。
- 接口：沿用超级管理员注册接口。
- 原型阶段保留该入口；生产部署时应增加邀请码、审批或初始化限制。
- 注册成功后返回 `/admin/login`。

### 5.4 租户管理员注册

- 字段：管理员姓名、邮箱、密码、确认密码、所属机构。
- 接口：沿用租户管理员注册接口。
- 注册成功后返回 `/admin/login`。

## 6. 页面设计

### 6.1 共用视觉语言

- 延续现有企业级蓝色 SaaS 风格。
- 左侧为系统定位、核心价值和身份说明，右侧为认证卡片。
- 两套入口使用不同的副标题、图形和强调色，用户能够立即判断当前所在系统。
- 登录、注册、找回密码保持一致的表单尺寸、错误提示和成功反馈。

### 6.2 客服与用户系统认证页

- 主标题强调“服务接待与在线咨询”。
- 登录卡提供“客服登录”和“用户登录”两个身份标签。
- 注册卡只提供“客服”和“用户”两种身份卡片。
- 用户登录成功后进入客户聊天页面，不再允许直接访问公开 `/chat`。

### 6.3 平台与租户管理系统认证页

- 主标题强调“平台运营与机构管理”。
- 登录卡提供“超级管理员”和“租户管理员”两个身份标签。
- 注册卡只提供“超级管理员”和“租户管理员”两种身份卡片。
- 页面增加“切换到客服与用户系统”的明显入口，反向入口同理。

## 7. 路由守卫

- `/platform/*`：仅 `platform_admin`。
- `/organization/*`：`tenant_admin`，超级管理员的租户上下文切换沿用现有逻辑。
- `/workbench/*`：`agent`；需要跨角色演示的管理权限另行保留明确规则。
- `/customer/*`：仅 `customer`。
- 未登录访问业务页面时，按目标页面所属系统跳转到 `/admin/login` 或 `/service/login`。
- 已登录但角色不匹配时，跳转到该角色的合法首页。

## 8. 会话与数据流

1. 用户在对应入口提交登录表单。
2. 前端调用现有 `/api/v1/auth/login`。
3. 后端验证账号，返回令牌、用户资料和角色。
4. 前端验证角色是否属于当前入口。
5. 匹配时保存会话并跳转角色首页；不匹配时显示入口错误且不保存会话。
6. 受保护页面通过统一路由守卫验证登录状态和角色。

两个入口使用同一后端和数据库，数据隔离继续依赖后端的 `tenant_id` 与角色权限，不通过前端页面隐藏代替后端鉴权。

## 9. 错误处理

- 账号密码错误：展示服务端认证错误。
- 账号角色与入口不符：提示正确入口并提供跳转按钮。
- 后端不可用：仅演示账号可在明确的离线错误下回退，认证拒绝不得触发回退。
- 注册字段错误：在字段下方显示具体校验信息。
- 用户未登录访问聊天页：跳转 `/service/login`，登录后返回 `/customer/chat`。

## 10. 测试与验收

### 10.1 自动化测试

- 四种角色分别解析到正确首页。
- 两个登录入口只接受各自的角色集合。
- 两个注册入口只显示各自的两个身份。
- 未登录访问四个业务首页时跳转到正确登录入口。
- 客户未登录不能访问 `/customer/chat`。
- 旧路由正确重定向到新入口。
- 明确的认证拒绝不会触发演示登录回退。

### 10.2 浏览器验收

- 两套登录注册页面在桌面端视觉完整，无重叠或裁切。
- 两个系统可分别在独立浏览器标签页打开。
- 四种演示身份登录后进入四个不同页面。
- 系统切换入口明确，不出现四身份混合注册界面。
- 用户注册、登录、进入咨询页面的主流程可完整演示。

## 11. 成功标准

- 原四身份混合注册页不再出现。
- 两个独立前端入口分别只承载两种身份。
- 四种身份的注册、登录和首页跳转边界清晰。
- 普通用户必须登录后才能咨询。
- 现有业务页面、后端接口和数据库数据继续可用。
