# 双客服同时上线 · 会话对接流程设计与实施计划

> 日期：2026-08-26
> 范围：设计“王五、张善两名客服同时上线”场景下的会话分配与对接流程，并给出前端实施计划（不改动现有代码）

---

## 1. 背景与目标

当前客服工作台（`/workbench`）的会话接入方式是**手动抢单**：客服点“一键接下一”（`App.jsx` 的 `claimNext`）或看板上的“接管”按钮（`ServiceWorkspace.jsx` 的 `claim`）自己认领会话。客服的“在线/忙碌/离线”状态（`AgentWorkspaceShell.jsx` 的 `presence`）只影响顶栏展示，**不参与实际分配**。

本设计要解决：当两名及以上客服同时在线时，新会话如何自动、公平、按技能分配到具体客服，并定义从客户进线到会话结束的完整对接流程。

**目标**
- 会话进入后有明确的分配规则，不再依赖人工抢单
- 两名客服同时在线时负载均衡、技能匹配、SLA 优先
- 客服状态（在线/忙碌/离线）真实影响分配
- 全程可观察：分配去向、排队原因、升级动作可追溯

---

## 2. 场景定义（王五、张善同时上线）

假设两名新客服同日上线：

| 客服 | 技能组 | 承接队列 | 可并发上限 maxLoad | 平均首响 |
| --- | --- | --- | --- | --- |
| 王五 | 售后支持 | 售后队列（after_sales） | 6 | 40s |
| 张善 | 售前咨询 + 售后支持 | 售前队列（pre_sales）、售后队列 | 5 | 45s |

两人 09:00 同时登录上线，工作台进入“在线接待”状态。

---

## 3. 总体对接流程（客户进线 → 会话结束）

```
客户发起咨询
   │
   ▼
① 会话创建（渠道：微信 / 网页 / 企业微信 / H5 / API）
   │
   ▼
② 身份与意图识别 → 分流入队
   ├─ 已购 / 退款 / 订单 / 故障 / 投诉 → 售后队列
   ├─ 企业版 / 功能 / 部署 / 报价     → 售前队列
   └─ 投诉与高风险                     → 投诉专线（升级）
   │
   ▼
③ 分配引擎匹配候选客服
   ├─ 队列类型 ∈ 客服技能组（queueKey 匹配）
   ├─ 客服状态 = 在线接待（presence=online）
   └─ 当前接待数 < maxLoad（未满载）
   │
   ▼
④ 候选集中选择承接人（负载均衡）
   最少接待数 → 轮询 → SLA 紧迫者优先给首响快的人
   │
   ▼
⑤ 推送分配结果到客服工作台
   会话列表置顶 + 未读徽标 + 顶部“新会话分配”提示
   │
   ▼
⑥ 客服接管（点击进入）
   ├─ 立即接管 → 状态 queued → human，绑定 assignee
   ├─ 超时未接管（60s）→ 回收重分配 + 通知
   └─ 忙碌/离线中 → 不参与分配，会话留在公共队列
   │
   ▼
⑦ 接待与协作
   消息 / AI 辅助 / 快捷回复 / SLA 时钟
   ├─ 技能不匹配 → 转接（按技能组选承接客服）
   ├─ 需协同    → 创建关联工单
   └─ 高风险    → 升级主管 / 投诉专线
   │
   ▼
⑧ 结束会话 → 客户评价 → 归档
   │
   ▼
⑨ 负载释放：接待数 -1，可接收新分配
```

---

## 4. 分配引擎规则

### 4.1 就绪客服池

- 客服登录后默认“在线接待”进入就绪池
- 状态切换：在线接待（可接新会话）/ 忙碌（保留名下会话，不再接新）/ 离线（名下待接管会话回收重分配）
- 就绪池 = 所有 presence=online 且未满载的客服

### 4.2 候选集匹配（决策树）

```
新会话进入分流队列
  └─ 队列类型（after_sales / pre_sales / escalation）
      └─ 在就绪池中筛选 queueKey 匹配该队列的客服
          └─ 当前接待数 < maxLoad
              └─ 得到候选集
候选集为空 → 会话留在公共队列排队 + SLA 倒计时 + 风险预警
```

### 4.3 承接人选择（按优先级）

1. **负载最低**：比较各候选当前接待中会话数，取最小者（数值均衡）
2. **轮询**：负载相同时，按最近一次分配时间轮流（时间均衡）
3. **SLA 优先**：会话已进入 warning/danger 时，优先分配给平均首响更快的候选
4. 命中唯一客服后写入 `assignee` 并推送

### 4.4 分配通知与接管

- 分配后会话在客服工作台会话列表**置顶 + 未读徽标 + 新会话提示条**
- 客服点击进入即完成接管（`status: queued → human`）
- **60 秒未接管**：会话自动回收回公共队列，重新走分配，并通知双方（原承接人 + 新候选人）

### 4.5 转接与升级

- 转接：目标技能组 → 在该组就绪客服中按负载最低选择；转出后原客服失去发送权限
- 升级：投诉/高风险会话进入投诉专线（escalation），仅专线客服或主管可接

## 5. 王五、张善示例推演

| 时间 | 事件 | 分配逻辑 | 结果 |
| --- | --- | --- | --- |
| 09:00 | 王五、张善同时登录上线 | 两人 presence=online，进入就绪池 | 就绪池 = {王五, 张善} |
| 09:01 | 会话 A：退款到账（售后队列） | 候选={王五, 张善}（张善含售后技能）；负载同为 0 → 轮询 | 王五接 |
| 09:03 | 会话 B：企业版部署（售前队列） | 候选={张善}（王五无售前技能） | 张善接 |
| 09:06 | 会话 C：API 故障投诉·紧急（售后） | 候选={王五(1), 张善(1)}；负载相同 → 轮询；SLA 已 warning，王五首响 40s < 45s | 王五接 |
| 09:10 | 会话 D：发票问题（售后） | 候选={王五(2), 张善(1)} → 负载最低 | 张善接 |
| 09:12 | 王五切“忙碌” | presence=busy，退出就绪池 | 新售后会话只推张善 |
| 09:15 | 会话 E：投诉（售后·高风险） | 张善接待数 3 < 5，但投诉类走升级路由 | 进入投诉专线等待 |
| 09:18 | 会话 F：登录密码（售后） | 王五忙碌、张善(3) 未满载 | 张善接 |
| 09:20 | 张善接待数达到 5（满载） | 满载退出候选 | 新会话排队 + SLA 预警 |
| 09:25 | 王五切回“在线接待” | 重新进入就绪池 | 排队会话按 SLA 优先分给王五 |
| 09:30 | 张善收到会话 G（售前） | 匹配售前技能 → 唯一候选 | 张善接 |

**负载均衡效果**：最终王五 3 个、张善 4 个（技能约束下），无人工干预、无会话积压。

## 6. 边界与异常处理

| 场景 | 处理 |
| --- | --- |
| 所有候选满载 | 会话留在公共队列，SLA 倒计时，看板“SLA 风险预警”升级 |
| 客服中途离线 | 名下“待接管”会话回收重分配；“接待中”会话保留或提示转接 |
| 客服忙碌 | 保留名下会话，退出就绪池，不再接新 |
| 60 秒未接管 | 会话回收重分配，双方收到通知 |
| 无技能匹配 | 进入公共队列等待，触发 A 队长/管理员介入 |
| 紧急投诉 | 绕过普通分配，直接进投诉专线 |
| 后端不可用 | 沿用本地演示数据与本地分配引擎，接口签名预留 `/api/v1/dispatch/assign` |

## 8. 项目计划

### 阶段一（P0）基础分配引擎 —— 约 2 天

| 任务 | 说明 | 验收 |
| --- | --- | --- |
| 1. presence 全局化 | 将在线/忙碌/离线提升为共享状态（sessionStorage + Context），看板与工作台同步 | 王五切忙碌后，看板立即显示，且不再接收新分配 |
| 2. 分配引擎纯函数 | 新增 `dispatchConversation(queue, agents)`：候选匹配 + 负载最低 + 轮询 + SLA 优先，返回 assignee | 单元测试覆盖：单候选、多候选负载均衡、满载排队、技能不匹配 |
| 3. 接管流程改造 | 新会话自动分配后置顶 + 未读徽标 + 提示条；点击接管绑定 assignee | 王五张善场景可完整演示 |
| 4. 未接管回收 | 60 秒未接管自动回收重分配 | 定时器触发回收，双方可见 |

### 阶段二（P1）负载均衡与升级 —— 约 2-3 天

| 任务 | 说明 | 验收 |
| --- | --- | --- |
| 5. 满载排队 + SLA 联动 | 候选满载时会话排队，SLA 预警看板实时反映 | 张善满载后新会话进入风险预警 |
| 6. 转接优化 | 转接弹窗改为按技能组实时列出在线承接人（负载最低优先） | 转接选择真实可用客服而非写死选项 |
| 7. 离线回收 | 客服离线时名下待接管会话自动回收重分配 | 王五离线 → 名下会话转移 |
| 8. 分配历史与审计 | 记录每次分配（会话、承接人、时间、算法依据） | 管理端可查分配记录 |

### 阶段三（P2）排班与策略配置 —— 约 1-2 天

| 任务 | 说明 | 验收 |
| --- | --- | --- |
| 9. 多技能组匹配 | 客服可配置多个 queueKey，按技能匹配而非单一队列 | 张善同时承接售前+售后 |
| 10. 分配策略配置 | 管理端可配置轮询/最少负载/权重比例 | 切换策略实时生效 |
| 11. 分配指标 | 平均分配延迟、负载均衡度、未接管率报表 | 看板展示指标卡 |

**合计约 5-7 天**（纯前端，沿用本地数据层；后端接口预留 `POST /api/v1/dispatch/assign`、`GET /api/v1/dispatch/history`）。
